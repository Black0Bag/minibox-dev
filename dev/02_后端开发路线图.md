## 0. 后端定位与技术底座

**定位**：单后端中枢——所有逻辑、数据存储、API、调度由 Go 进程承担；后端无任何前端（含全功能 CLI）。

| 维度 | 约束 |
|---|---|
| 语言 | Go 1.25+，零 CGO |
| 数据库 | modernc.org/sqlite（WAL，读写分离）+ FTS5(trigram 中文) + sqlite-vec 向量 |
| HTTP | chi v5 + SSE（Go 原生 Flusher）+ go-chi/cors + go-chi/httprate |
| MCP | mark3labs/mcp-go（stdio + Streamable HTTP） |
| 弹性 | sony/gobreaker + cenkalti/backoff/v4 |
| 配置 | YAML + spf13/viper 热更新 |
| 日志 | log/slog + lumberjack 轮转 |
| WS | coder/websocket |
| 时间 | beevik/ntp 校准 |
| 迁移 | pressly/goose（嵌入模式） |
| 单实例 | gofrs/flock |
| 端口 | 8086（可配：config + `--port` 覆盖） |
| API | 统一 `/api/v1/` 前缀，RFC 7807 错误格式 |

## 4. 后端注意事项（踩坑红线）

1. **零 CGO 是铁律**：引入任何 CGO 依赖前必须否决（交叉编译路由器 arm64 全靠它）。
2. **版本号单一来源**：只定义一次 `Version`，`-ldflags` 注入（旧版双变量坑）。
3. **端口一致性**：代码/配置/文档统一 8086；启动打日志、健康检查返回实际端口。
4. **SSE 必须 Flush()**：SSE 路由不能用 `middleware.Timeout`，用独立路由组。
5. **日志与数据库分离**：logme 用纯文本追加（不进数据库，数据库日志多了会锁死）。
6. **升级脚本**：不依赖 procd restart，用 nohup/exec；升级前先做数据库快照。
7. **二进制部署**：路由器用 SFTP 传输，不用 base64 管道（大文件会溢出）。
8. **路由器自启**：rc.local + nohup（procd 不可用）。
9. **五重守卫**：StopGuard / SubagentContextGuard / StepCounter / PermissionGuard / MaxToolCalls。
10. **提交前**：`go vet` + `go test ./...` + `golangci-lint`（CI 已配置，push 即自动跑）。

## 5. 决策确认记录（滚动追加）

### Q-01 双区制 + 概率蒸馏数据库 schema — ✅ 已确认（2026-08-08）

**缓存区淘汰方式**：方案 C（时间窗 + 容量上限双保险）
- 超过时间窗（默认 7 天）未编译的缓存条目自动清除
- 超过容量上限（默认 1000 条）时按 LRU（最近最少访问）淘汰
- 两道保险，谁先触发谁生效
- 参考行业实践：Redis/Memcached 的 maxmemory + TTL 双保险模式

**偏好概率更新方式**：方案 C（证据数加权）
- 公式：新概率 = 旧概率 × (证据数 / (证据数 + 1)) + 本次行为分 × (1 / (证据数 + 1))
- 证据越多，单次行为对概率影响越小（老偏好不易被一次矛盾推翻）
- 与已定 T-07 五机制（TTL 衰减/重要性加权/选择性遗忘/老化淘汰/删除归一化）完全一致

**推荐 schema（5 张表）**：
- kb_cache（缓存区）→ Agent 临时写入，待编译，带 processed 标记 + LRU + TTL
- kb_store（存储区）→ 编译后正式知识，带分类/访问计数/最后访问时间
- kb_vectors（向量表）→ sqlite-vec 虚拟表，关联 kb_store
- kb_preferences（偏好表）→ 蒸馏偏好，6 字段（关键词/概率/来源强度/证据数/最近命中时间/重要性分）
- kb_snapshots（快照表）→ VACUUM INTO 版本管理，带回滚原因字段

**互联网校准来源**：Google AI 概览 + GitHub 开源 AI agent memory system 通用模式（三表+向量表），minibox 在此基础上额外增加快照表和精细化蒸馏字段。

### Q-08 logme 与双区制代码级交互 — ✅ 已确认（2026-08-08）

**核心结论**：logme 与知识库是两个物理分离的独立系统，不互相写入，不数据同步。

**logme 的两个用途（用户澄清）**：
1. **给用户看的"到访留言条"**：Agent 操作文件后留下记录，用户翻文件夹时知道 Agent 来过、做了什么
2. **给 Agent 自己看的"文件夹说明书"**：Agent 下次来到同一文件夹，先读 logme 获取摘要（有什么文件/用途/注意事项/操作权限），避免重复遍历，省 token 省上下文

**过期检测机制**：方案 B（mtime 快照校验）
- logme 记录写入时的文件列表 + 各文件修改时间（mtime）
- Agent 下次读取 logme 时，先比对当前实际文件状态
- 文件未变 → logme 有效，直接复用，省 token
- 文件已变 → logme 过期，重新遍历，覆盖写 logme
- 与已定"时间戳机制全局化"理念一致，实现成本极低（fsutil wrapper 顺便记 mtime）

**两套系统边界**：
- 数据库内部操作（增删改查知识条目）→ 不写 logme
- 磁盘文件操作（创建/读写/删除文件）→ 写 logme
- 两套数据物理分开，删 logme 不丢知识，删知识库不丢文件记录
- logme 是可丢弃的缓存（懒加载覆盖写），知识库是持久化记忆

**logme 跨前后端传播**（用户补充）：
- logme 不限于后端本地服务器，前端 APP 在手机上进行文件浏览/操作时同样留 logme
- 前端 APP 的设备控制层（无障碍+Shizuku）执行文件操作时，也需生成 logme 文件
- 涉及前后端路线图交叉修改，前端 F3 设备控制阶段需同步落地

**互联网校准来源**：Google AI 概览 2026——行业共识为"文件级元数据缓存"与"全局知识库"应物理分离（SSoT 原则），logme = 去中心化上下文（Decentralized Context），过期检测采用 mtime 校验 + 懒加载覆盖模式。

### Q-06 事件体系统一化 — ✅ 已确认（2026-08-08）

**结论**：采用统一信封模式（Normalized Event Envelope），不再搁置。

**统一信封格式**：
```json
{
  "spec_version": "1.0",
  "event_id": "evt_01j8m4x...",
  "trace_id": "trc_99a8b7c...",
  "timestamp": "2026-08-08T14:30:00Z",
  "producer": "agent.planner_v2",
  "type": "agent.tool_call",
  "data": { ... }
}
```

**三通道统一**：
- REST → type=`api.response`（同步一问一答）
- SSE → type=`agent.thinking` / `agent.answer_delta` / `agent.tool_call` / `agent.context_meta`（保留已有事件格式，套进信封）
- WS → type=`device.*`（设备控制、工具调用、中断）

**三个最佳实践**：
- 幂等性：event_id 去重，重复送达不重复执行
- 可追踪：trace_id 贯穿一次任务的所有事件，跨通道可审计
- 版本化：spec_version 写在消息里，开源后前端旧版可兼容提示

**与已有设计的关系**：
- 已有 SSE 统一事件（thinking/answer/tool/context_meta）保留，只加信封外壳
- 已有 seq 断线续传机制保留，seq 作为 data 内字段
- trace_id 和 event_id 与已定"时间戳全局序号"机制一脉相承
- 趁前端 F0 协议地基未写，统一成本最低

**互联网校准来源**：Google AI 概览 2026——行业共识为统一信封模式（Normalized Event Envelope），三条通道各司其职但消息格式统一，trace_id 跨通道追踪，spec_version 版本化兼容。
