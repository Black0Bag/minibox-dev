## 6. 技术论证记录（2026-08-06 15:50:00）

> 以下为基于互联网调研 + 交叉审计对后端路线图不完善之处的技术论证，仅记录分析意见，不替用户做任何决定。

### 论证 T-01：向量搜索方案应考虑升级为 sqlite-vec 虚拟表

**当前路线图方案**：Phase 1.1 采用 BLOB in SQLite + 纯 Go 全表扫描余弦相似度（sage-wiki 旧方案）。

**互联网调研发现**：
- `modernc.org/sqlite` 自 v1.47.0 起已内置 `sqlite-vec` 向量搜索扩展（纯 Go，无 CGO）。
- GitHub 上有 `viant/sqlite-vec` 纯 Go 实现，专为 modernc.org/sqlite 设计。
- sqlite-vec 支持 KNN 查询、quantization、SIMD 加速，性能远超全表扫描。
- Reddit r/golang 社区确认：modernc.org/sqlite 的向量扩展使语义搜索比 FTS 更简单。

**论证意见**：路线图参考文档已提到「v1.55.0 起内置向量搜索虚拟表」，但 Phase 1.1 的任务描述仍沿用旧方案（BLOB+全表扫描+纯 Go 余弦）。建议在 Phase 1.1 中新增子任务，评估 sqlite-vec 虚拟表替代纯 Go 全表扫描的可行性，尤其是知识库增长后全表扫描的性能瓶颈。这是优化项，不影响架构设计。

**状态**：记录待用户斟酌。

### 论证 T-02：时间戳组件的 NTP 同步应有明确库选型

**当前路线图方案**：Phase 0.5 「统一时间服务（系统时钟+NTP校准）」，未指定具体库。

**互联网调研发现**：
- `beevik/ntp`（GitHub：github.com/beevik/ntp）是 Go 生态最成熟的 NTP 客户端库，基于 RFC 5905 实现 SNTP 客户端，纯 Go 无依赖，支持查询远程 NTP 服务器获取时间偏移。
- 以及 `beevik/nts`（Network Time Security，NTS 安全版），适合对时间真实性要求更高的场景。

### 论证 T-07：概率蒸馏数据结构应有衰减机制防止历史污染

**当前路线图方案**：Phase 1.4 概率蒸馏数据结构（关键词+概率+来源强度+证据条数+最近命中时间），Phase 4.5 贝叶斯后验（命中上调/反例下调）。路线图滚动追加 08-03 AI 建议了「行为失败反向衰减」但未拍板。

**论证意见**：建议 Phase 1.4 / Phase 4.5 中补充分散衰减策略：时间衰减（定期降低长期未命中概率）+ 归一化（防止概率膨胀）+ 老化淘汰（低概率+低证据自动标记待清理）。这些是纯系统行为（非 LLM 决策），可硬编码实现，不需用户每次决策。与路线图滚动追加 08-03 中 AI 建议的第 4 点（每条偏好携带元数据：证据条数/最近命中时间/来源会话）天然配合——衰减基于这些元数据自动计算。

### 论证 T-09：Phase 0 logme 防火墙的 diff 检查需考虑并发写入场景

**当前路线图方案**：Phase 0.3 防火墙代码级 enforce——校验新内容只追加末尾、未修改已有行（diff 检查）。

**技术分析**：subagent（Phase 2.5）并行执行时，多个 goroutine 可能同时访问同一文件夹的 logme 文件。防火墙的 diff 检查 + 追加写入必须是原子操作，否则：
- goroutine A 读取文件做 diff → 通过 → 准备追加
- goroutine B 在 A 追加前也读取文件做 diff → 通过 → 也准备追加
- A 先追加 → B 追加时会追加到 A 的内容后面（可能通过 diff，也可能触发误判）

**论证意见**：建议 Phase 0.3 明确 logme 写入采用 `sync.Mutex`（按文件路径加锁）+ 原子追加模式：读取当前文件 → diff 校验 → 追加新内容 → 释放锁，全流程在互斥锁保护下完成。序号分配（Phase 0.4）同样在此锁内完成，保证序号与写入原子一致。这与路线图滚动追加 18:46「序号必须由后端统一分配（写入唯一入口）」完全一致——锁 + 原子写入 = 唯一入口。

func logmeAppend(filepath string, newContent string) error {
    logmeMu.Lock()
    defer logmeMu.Unlock()
    // 1. 读取当前文件
    // 2. diff 校验——只追加末尾，未修改已有行
    // 3. 分配序号（锁内分配保证原子一致）
    // 4. 原子追加（O_APPEND 模式）
    // 5. 释放锁（defer）
    return nil
}

### [2026-08-07 15:40:00] N-15（Q-03）落实：资源自适应降级——四级状态机 + 迟滞带 + 能力联动

**问题意义**：项目开源面向未知设备（MT6000 路由器 128-512MB ~ PC 8GB+），同一份代码必须自动适配——弱设备「能用但功能少」，而非「直接崩溃」。核心承诺兜底：「核心功能永远保，补充功能先限后禁」。

- PraisonAI：Resource-Based + Capability 双维度降级

**落实内容**：

**一、功能分类**：
| 类别 | 功能 | 降级策略 |
|---|---|---|
| 核心（永不关） | REST API / WS 保活 / 健康检查 / 日志 | 任何等级保留 |
| 核心（可降级） | 知识库查询 | L3 降为 FTS5 关键词搜索兜底 |
| 补充（先限后禁） | subagent 并行 / 编译管道 / 蒸馏 | 逐步限频 → 暂停 |
| 补充（禁掉） | 备份推送 / 浏览器工具 / 通知推送 | 高等级直接禁 |

**二、四级状态机（触发条件连续 30s）**：
| 等级 | 触发 | subagent 并发 | 编译/蒸馏 | 向量搜索 | 备份/浏览器 |
|---|---|---|---|---|---|
| L0 正常 | 无 | 2 | 正常 | 启用 | 启用 |
| L1 轻度 | CPU>70% 或 内存>70% | 2→1 | 限频 | 启用 | 启用 |
| L2 中度 | CPU>85% 或 内存>85% 或 磁盘<15% | 1→0 | 暂停 | 保留 | 暂停 |
| L3 重度 | 内存>95% 或 OOM 风险 | 0 | 暂停 | FTS5 兜底 | 暂停 |

**三、迟滞带防抖**：
- 降级触发：连续 30 秒超阈值
- 恢复条件：连续 60 秒低于（阈值-5%）
- 目的：防内存 71%↔69% 抖动导致 L0/L1 反复横跳

- 恢复无需重启——全部运行时开关控制
