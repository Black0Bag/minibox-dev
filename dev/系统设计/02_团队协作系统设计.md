## 一、概念定位

将 Agent 系统组织为一个「大型服务型公司」：

- 用户 = 甲方客户
- 对话框 = 公司前台（老板）
- 各专业领域 = 多个项目组（团队）
- 每个团队 = 组长 + 多名专职成员（各有独立人格、职责细分、可互相讨论）
- 团队可自进化：成员发现人手不足 → 逐级上报 → 新建专职子员工人格加入

## 二、三种工作模式（用户已确认）

用户在对话框中通过**模式选择器**手动选择，随时可切换：

| 模式 | 工作机制 | 角色 | 适用场景 |
|---|---|---|---|
| **对话模式** | 一问一答，不用工作流 | 单个 Agent 直接应答 | 日常问题、简单查询、聊天 |
| **Plan-Build 模式** | 正常的 to-do list + subagent 工作流 | 单个 Agent：先出方案 → 用户确认 → 再执行 | 中等复杂度任务，需要先审方案 |
| **项目模式** | 专业人员替代 to-do list 和 subagent | 完整专业团队接管：前台分诊 → 团队组建 → 成员讨论 → 自行拆解执行 | 大型任务，需要多人协作 |

### 模式间关系

- 可随时升档/降档（对话 ↔ Plan-Build ↔ 项目）
- 高级模式可随时退回低级模式继续对话
- 每次对话开始时用户选择本次使用的模式

### Plan-Build 模式细节（用户已确认）

- Plan 阶段：Agent **禁写**，只分析和出方案文本 → 暂停等待用户审阅
- Build 阶段：用户确认方案后，同一 Agent 获得执行权限（工具白名单动态扩展）
- 审批环节不可跳过

### 项目模式流程（用户已确认方向）

1. 前台接客：与「客户经理」对话，分析需求，建议「派哪个团队办理」
2. 用户确认团队 → 团队界面展示（组长介绍，成员就绪）
3. 讨论阶段：成员互相讨论（内部进行，用户看到进度状态）
4. 方案阶段：组长向用户汇报方案文本，用户审阅
5. 执行阶段：团队执行，用户可看到各成员进展摘要
6. 结案：组长交付成果，用户确认 → 团队配置存入知识库 → 解散

## 三、团队组织架构

```
用户（甲方）
  └─ 前台/老板（分诊路由，不亲自干活）
       ├─ 团队A「编程」 ── 组长 ── 成员1(调研员) / 成员2(分析师) / 成员3(执行者) / ...
       ├─ 团队B「创作」 ── 组长 ── 成员...
       ├─ 团队C「办公」 ── 组长 ── 成员...
       └─ ...（按需扩充）
```

### 成员职责边界（用户已确认方向）

- 每个成员只干自己的份内工作（工具白名单物理限制）
- 成员之间可互相讨论（横向协作），不只是纵向汇报
- 上级下达任务 → 成员互相讨论 → 与组长讨论 → 定下基调 → 做出成果交差

### 自进化机制（用户已确认方向）

- 成员发现团队人手不足 → 逐级向上反馈
- 主管审批 → 自动新建专职子员工人格加入团队
- 新建人格来源：人力资源市场模板库优先 → 现场生成兜底 → 生成后入库复用

## 四、角色卡系统

```
1. 角色与核心身份：是谁、擅长什么、怎么思考
2. 约束与边界：什么不能做、安全限制
3. 工具授权：能用哪些工具
4. 输出规范：输出格式、语气、结构
```

## 五、绩效与评估机制（讨论中，未最终定稿）

用户对「概率蒸馏奖惩」方案表示不稳妥，已搜索业界更优方案，当前推荐方向为**三层综合评估**：

1. **系统自动记分**：成功率、效率（步数）、返工率——无需额外 LLM 调用
2. **同事互评（LLM-as-a-Judge）**：组长对成员产出做评语，记入成员档案
3. **甲方确认（HITL）**：用户对最终成果点「满意/不满意」，权重最高

评估结果影响：下次同类任务成员被选中的优先级；长期不用 + 差评多 → 自然淘汰。

> ⚠️ 此机制尚未经用户最终拍板，待后续讨论定稿。

## 六、资源管理（用户已确认方向）

- **每个成员可独立配置 LLM 模型**：在设置中管理每一位成员使用的模型（供应商 + 模型 + 思考强度）
- **串行/并行可配**：根据实际情况决定成员讨论/执行采用单线程顺序执行还是并发执行（设置中管理）
- **预算控制**（待细化）：Token 总量限制、并发上限、超时限制

## 九、风险与对策（已搜索业界经验）

| 业界风险 | 对策 |
|---|---|
| 上下文爆炸 | 侧链日志：讨论写独立文件，主上下文只收回摘要 |
| 错误传播放大 | 交叉校验 + 三层评估 + 不同成员用不同供应商模型（对抗群组思维） |
| 通信混乱/死锁 | 讨论协议设超时上限、回合上限、组长最终决定权 |
| 编队税（通信成本 n(n-1)/2） | 团队规模上限控制，初始团队 3-5 人 |
| 成本爆炸 | 资源预算控制 + 串行优先、按需并行 |
| 自进化失控 | 新建成员上限 + 瘦身淘汰机制 |
| 意图漂移 | 用户原始需求作为不可变基准，成果产出时比对 |

### [2026-08-06 23:20:00] 第 3 项落实：自进化审批规则

**用户决策**：HR 独占人员调动权 + 增派预警 + 超标需用户审批。

**落实内容**：

1. **HR 是独立常设角色**：不属于任何团队，不参与生产。唯一拥有人员调动最终审批权。

2. **三层审批流程**：
```
团队成员：「我这边干不了，需要增派人手」
     ↓
团队组长：评估「真的缺人吗？不加能不能内部调配解决？」
     ├─ 可调配 → 内部解决，不上报
     └─ 确实缺人 → 上报 HR
     ↓
人力资源部（HR）：审核「什么专业？临时还是永久？模板库有没有？不加行不行？」
     ├─ 驳回（不必要/可临时借调）→ 团队自行克服
     ├─ 批准（常规专业、模板库有现成）→ 从模板库招人
     └─ 专业性太强/模板库没有 → 向上反馈
     ↓
（专业性太强或超标时）HR → 用户：「需要你裁决」
     ├─ 用户同意 → 现场生成新人格 + 入库
     └─ 用户不同意 → 团队自行克服
```

3. **增派预警机制**：
   - 一次任务中增派 **1 人**：HR 正常审批，无需用户介入
   - 一次任务中增派 **第 2 人**：系统自动预警（相当于黄色警报），HR 审批时需特别审慎
   - 一次任务中增派 **第 3 人及以上**：HR 必须向用户反馈审批，用户点头才可继续

4. **新建人格来源**：先从模板库取（快），取不到才现场生成（异步进行，不打断其他工作）。生成后入库存为可复用角色卡。

5. **临时 vs 永久**：
   - 临时：本次任务用完即走（不入库，不留档案）
   - 永久：入职存档案（入库，下次同类任务可复用）
   - 由 HR 判断或组长申请时标注

6. **驳回机制**：每一层均可驳回——组长说「不用加」、HR 说「不批/不必要」、用户说「不同意」。驳回后团队自行克服。

### [2026-08-06 23:40:00] 第 4 项落实：讨论协议细节

**用户决策**：确认全部六个子项（含业界调研调整后的 4a 和新增 4f）。

**落实内容**：

**4a 讨论格式：独立提案 + 批评（IPP 模式）**
- 成员先各自独立形成观点（独立推理，不互相影响）
- 然后进入批评阶段：其他成员可挑战、可反对，但不强求达成一致
- 组长汇总各方意见后定夺
- 业界依据：2025 年最新研究（Free-MAD / L-MAD）表明，不强求共识比强制共识更准——避免盲从和集体幻觉

**4b 说话顺序：组长点名制**
- 组长决定谁先发言、谁接着说
- 不允许自由抢答，防止撞车或等待

**4c 讨论轮次：固定上限 + 组长可提前结束**
- 最多 5 轮讨论
- 组长认为第 3 轮已充分即可提前停
- 业界依据：超过 5 轮讨论开始引入噪声、偏离原始问题

**4d 意见分歧：组长裁决为主**
- 分歧时组长听取双方意见后直接定方向
- 仅在涉及「需要用户做决定的事情」（加人、危险操作等）才上报用户
- 业界依据：2025 年研究肯定第三人裁决优于强共识

**4e 并行/串行规则：依赖检测 + 资源冲突检测**
- 有依赖（A 的产出是 B 的输入）→ 串行
- 操作同一资源（如改同一个文件）→ 串行
- 无依赖且不碰同一资源 → 可并行
- 判断由组长在分派时完成（业界 DAG 有向无环图调度模式）
- 额外保障：并行的成员各自在独立工作区操作（T-05 侧链日志 + 独立 State 已覆盖）

**4f 问题锁：原始需求锚定（新增）**
- 用户原始需求作为不可变基准
- 每轮讨论结束后，组长对照基准确认讨论未偏移
- 若检测到偏移 → 组长立即拉回正题
- 业界依据：轮次越多 AI 越容易偏离原始问题，锚定机制可对冲漂移

### [2026-08-07 00:05:00] 第 5 项落实：绩效评估机制——信任档案

**用户决策**：认同「信任档案」替代「三层考核制度」，7 个维度全部拉满，衰减按对话次数而非天数。

**落实内容**：

**核心理念**：不是「任务结束打分」，而是每个角色卡拥有一个**持续动态更新的信任档案**——贯穿角色全生命周期，实时流动、持续衰减、自动淘汰。

**七维信任评分**：

| 维度 | 含义 | 计算方式 |
|---|---|---|
| **成功率** | 交给这个成员的活干成了没 | 完成数 ÷ 总分配数 |
| **推理一致性** | 中途有没有推翻自己、前后矛盾 | 对话过程中前后矛盾次数统计 |
| **工具调用准确率** | 用工具时参数对不对、有没有乱调 | 正确调用 ÷ 总调用 |
| **合规度** | 有没有越权操作 | 违规次数（超出工具白名单、越权操作） |
| **结算率** | 有没有中途崩溃重试浪费 | 正常完成 ÷ (正常 + 崩溃 + 浪费重试) |
| **维护衰减** | 多久没被用了 | 距上次使用对话次数 → 每次主对话未使用扣减信任分 |
| **反刷分保护** | 有没有成员互评中互相刷好评 | 检测异常评分模式（如成员间互评全好评） |

**衰减机制**：按主对话次数（非天数）——每次主对话轮次中未被指派的成员，信任分自动扣减（如每次扣 0.01）。长期不被用到 → 信任分自然降到阈值以下 → 自动标记「待退役」→ 超过下限 → 角色卡标记为「已退役」，不再被指派。

**信任等级**（示例）：
- Level 5（≥4.5）：核心骨干，优先指派
- Level 4（3.5-4.5）：常规使用
- Level 3（2.5-3.5）：观察期，减少指派
- Level 2（1.5-2.5）：警告期，仅在无其他选择时指派
- Level 1（<1.5）：退役区，不再指派

**信任档案示例**：
```
角色卡：调研员A
─────────────────
信任等级：Level 4（4.2/5.0）
成功率：92%（最近10次任务）
推理一致性：高（最近3次无矛盾记录）
工具调用准确率：88%
合规度：零违规
结算率：95%
上次使用：3 次主对话前
反刷分：无异常
档案记录：累计 27 次任务，25 次成功，2 次因数据源失效
最近评语（组长）：资料搜集全面但时效性需加强
最近评语（用户）：满意
```

**评估结果用途**：

| 信任等级 | 后果 |
|---|---|
| Level 5 | 优先指派，高频使用 |
| Level 4 | 正常使用 |
| Level 3 | 观察期，减少指派 |
| Level 2 | 警告期，仅无其他选择时指派 |
| Level 1 | 退役，不再指派，角色卡归档 |

**淘汰机制（三种降权）**：
- 维护衰减：长期未被指派 → 信任分自然下降
- 运行时降级：突然出现异常行为（推理矛盾、工具乱调、违规）→ 立即降权
- 分层筛查淘汰：静态分析 → 实时行为 → 用户反馈，多层过滤

**与现有系统集成**：
- 信任档案存入知识库（Markdown 文件，与「知识库=唯一记忆」铁律一致）
- 信任分变化写入 logme（留痕可审计）
- 反刷分保护依赖 T-05 侧链日志（互评记录可追溯）

### [2026-08-07 00:15:00] 第 6 项落实：预算控制规则

**用户决策**：不设预算限制（最大化 LLM 能力），仅供应商级并发控制，三层超时充分拉长。

**落实内容**：

#### 二、subagent 包架构（用户核心构想）

```
普通模式：主 Agent → subagent（一级，互相独立，一轮结束）

项目模式：主 Agent → subagent「包」
  包外看：主 Agent 发一个任务，包接住，交付一个结果
  包内看：多级嵌套
    Level 2: 组长
      Level 3: 成员A（可能有子员工）
        Level 4: 子员工
          Level 5: 终端工人
      Level 3: 成员B
      Level 3: 成员C
  
  包内所有记录不计入主对话上下文（侧链日志隔离）
  用户可主动「读取记录」（内部反思大会）强行加载包内记录到正文上下文
  业界无此功能——Claude Code 中间记录丢弃后不可恢复，本项目保留可回溯性
```

#### 四、换团队触发条件：外部熔断器

**核心原则**：AI 不会主动承认无法胜任（业界多份研究证实——Forbes 2026-06、Stanford 2026-03、MindStudio 2026-03），因此换团队**不靠团队自评**，靠**独立外部监控**。

**熔断触发条件（任一命中即触发）**：

| 条件 | 阈值 | 说明 |
|---|---|---|
| 连续失败 | ≥3 次 | 团队在同一子任务上连续失败 3 次 |
| 死循环检测 | ≥3 次 | 同一子任务被重复执行 3 次（来回做同一件事） |
| 产出未通过质检 | 连续 3 轮 | 团队产出物连续 3 轮未通过质量检查 |
| 整体超时 | 2 小时 | 团队整体未交付（与第 6 项全局超时一致） |
| 成员降级 | ≥2 人 | 同一团队中 ≥2 名成员信任档案降至 Level 2 以下 |

**触发后流程**：
```
熔断器触发 → 自动暂停团队 → 前台汇报用户：
「XX 团队似乎遇到了困难：
 - [具体原因]
 - 建议：A. 给当前团队 1 次补充资源的机会 / B. 直接换团队 / C. 中止项目由你直接介入
 请选择」
```

**用户主动权**：用户任何时候可按「中止/换团队」按钮，无需任何理由，不需等待熔断触发。

**业界依据**：
- Forbes (2026-06-25)：AI 不知道自己在犯错，行动时带有毫不动摇的自信
- Stanford (2026-03-26)：谄媚问题——AI 过度附和，永远不会说「我不行」
- Substack (2026)：「You Can't Just Monitor AI Agents — You Need to Stop Them」——不能只监控，必须能强制停止
